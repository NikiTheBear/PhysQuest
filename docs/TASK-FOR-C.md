## 0. 先搞清楚你在做什么

这个项目叫 **探理实验室 PhysQuest**，是一个让学生「先猜一句，再自己动手把物理实验调出来」的网站。

你负责的是**内容**：知识卡上学生看到的那些中文。

**你不写代码。** 你改的是六个 JSON 文件里的文字。改完跑一个脚本自检，通过就行。

## 2. 你手上有什么素材

在项目根目录下，有三个目录是你的：

### `shared/knowledge-data/card-text/` —— 卡片正面的「打个比方」和「为什么」

六个文件，一个领域一个：

```
card-text/mechanics.json          46 → 现在 41 条（振动与波搬到声学了）
card-text/electromagnetism.json   42 条
card-text/optics-university.json   6 条（只有大学的，其余在 optics-lens/knowledge.json）
card-text/thermodynamics.json     26 条
card-text/modern.json             20 条
card-text/acoustics.json          10 条
```

格式是「知识点 id → { analogy, why }」：

```json
{
  "K-M1-01": {
    "analogy": "推购物车：你往前推它就走，松手它慢慢停。想让它停得更快，就得往反方向拉一把。",
    "why": "力改变的是速度，不是位置。推的方向和运动方向一致就加速，相反就减速。生活里总觉得「要一直推才动」，其实是因为有摩擦力一直在偷偷拉你后腿。"
  }
}
```

### `shared/knowledge-data/card-detail/` —— 卡片正面的四块加厚内容

同样的六个文件（`optics.json` 是 32 条完整版）：

```json
{
  "K-M1-01": {
    "detail": ["第一段", "第二段", "第三段"],
    "compare": [{ "with": "易混概念", "diff": "一句话说清区别" }],
    "everyday": ["场景1", "场景2", "场景3"],
    "selfCheck": [{ "q": "问题", "a": "答案" }]
  }
}
```

**这四个字段的长度要求**（现在全部达标，你改写时保持）：

| 字段 | 要求 |
|---|---|
| `detail` | 2–3 段。第一段 120–200 字讲透机制；第二段 80–150 字讲公式/边界；第三段可选 60–100 字讲和相邻知识点的关系 |
| `compare` | 1–3 条，`diff` 要一针见血 |
| `everyday` | 2–4 条，20–50 字，要有画面感 |
| `selfCheck` | 正好 3 条，从易到难（是不是 / 为什么 / 换个条件还成立吗），答案 30–80 字 |

### `shared/knowledge-data/knowledge-prompts.json` —— 卡片背面的搭建方案

176 条，每条是一份完整的实验说明。**这个文件你不用自己写**，但如果某个知识点的实验搭不出来，你要能指出来。

## 3. 你的活，按优先级排

### 🥇 第一优先：热学和近代的 46 条知识点

**为什么最要紧**：这两个领域**一个能动手的关卡都没有**。学生点进去只有卡片，看不到实验。这是内容上的最大窟窿。

平台没有热学和近代的求解器（没有温度场、没有量子态），所以**不能靠加关卡解决**。能做的有两件事：

**做法 A：给这 46 条写「为什么做不出来」的诚实说明**

在卡片正面加一句，告诉学生「这一条为什么只能读、不能做」。这不是敷衍——**老实说明比假装能做要好**。

格式：改 `card-detail/thermodynamics.json` 和 `card-detail/modern.json` 里对应条目的 `detail` 第三段，或者在 `why` 里点一句。

**做法 B：给这些知识点各写 2–3 道手写题**

现在这 46 条的题全部是从提示词派生的，题目偏公式化。你手写一批「有真实情境」的题，质量会明显不一样。

参考现在光学那 59 道手写题的风格（在 `apps/web/src/data/question-bank.ts` 的 `HANDWRITTEN` 数组里），长这样：

```ts
{
  id: 'BQ-O1-01-easy',
  knowledgeId: 'K-O1-01',
  level: 'easy',
  type: 'single',
  question: '打开手电筒，光为什么能照到对面的墙上？',
  options: ['光沿直线一直往前走，碰到墙才停下', '光会自己拐弯去找墙', '光是墙发出来的'],
  answerIndex: 0,
  explanation: '光在同一种物质里沿直线传播。手电筒对着墙，光就直直地走过去，照到墙上被挡住，那里就亮了。',
  optionNotes: [
    '对。光在同一种物质里沿直线传播，碰到不透明的东西才停。',
    '光不会自己找路。它只会沿直线走，走不通就过不去。',
    '墙自己不发光，你看见它是它把照过来的光反射回你眼睛里。',
  ],
}
```

**注意 `optionNotes`**：这是逐项解析，长度必须和 `options` 一样，每个选项一条（含正确答案）。**这是这个题库最重要的部分**——学生答错时，要能看到每个选项为什么错。

### 🥈 第二优先：补误区库

**现在只有 10 条误区，挂了误区的卡片只有 8 张（176 张里）。**

这是个大问题：错题本靠误区工作，没有误区就没法把错题对应到知识卡。

你要做的：给每个领域挑出**学生真的会犯的错**，写成：

```json
{
  "id": "MIS-O2-05",
  "belief": "物体离透镜越近，像一定越大",
  "truth": "只在成实像（u > f）时成立。u < f 时物体越靠近透镜，虚像反而越小。",
  "challengeId": "CH-O2-04"
}
```

现有误区文件：`shared/knowledge-data/optics-lens/misconceptions.json`（10 条，全是光学的）。

**建议先做力学和电磁**，这两个领域有实验台，学生真会操作、真会错。

**目标：每个领域至少 8 条，总共 40–50 条。**

### 🥉 第三优先：老师使用手册

目录 `docs/handbook/`，现在是空的。

建议四个文件：

```
01-五分钟上手.md       第一次打开，从哪点起
02-一节课怎么安排.md    45 分钟怎么分配（最实用）
03-常见问题.md         打不开、光屏上没像、没法提交……
04-接AI（可选）.md      想用 AI 功能怎么配
```

**你独有的优势**：你本身就是新手。你摸索的每一步，就是真实老师会卡住的地方。

每写一条问自己：**一个从没用过这东西的老师，看得懂这句话吗？**

## 5. 怎么写（这是最要紧的一节）

### 5.1 `analogy` —— 打个比方

**一句话：找一个学生在生活里真的见过的东西。**

| ❌ 不合格 | ✅ 合格 |
|---|---|
| 凸透镜是一种会聚透镜。 | 正午把放大镜对准太阳，最亮的那个点就是焦点——这是你唯一能用尺子量出来的镜头参数。 |
| 虚像不能成在光屏上。 | 像镜子里的你——你伸手过去，那边什么也没有。 |

- 举的东西必须是初中生见过的（手机、放大镜、眼镜、投影仪、照相机、镜子、水里的筷子）
- 不要「就像……一样」这种空比喻，要有具体画面
- **20–60 字**

### 5.2 `why` —— 为什么

**不是「是什么」，是「为什么会这样」。**

| ❌ 不合格 | ✅ 合格 |
|---|---|
| 因为物距变大时像距会变小。 | 公式 1/f = 1/u + 1/v 里，u 变大，1/u 就变小，1/v 就得变大才能凑够 1/f——所以 v 变小。不是「记规律」，是算术。 |
| 虚像是假的像。 | 折射后的光线仍然是发散的，它们不会在透镜后面相交，只有反向延长才交于一点——所以叫虚像。 |

- 必须解释**机制**，不能重复结论
- **40–120 字**
- 不要写「记住这个规律就行」

### 5.3 `detail` —— 讲透一点

三段，各管一件事：

1. **是什么、为什么、关键在哪**（120–200 字，要有因果链）
2. **公式每一项什么意思 / 什么条件下失效 / 有什么反例**（80–150 字）
3. **和相邻知识点的关系**（60–100 字，可选）

学段要对：小学不要出现公式符号，大学可以出现微积分。

### 5.4 `compare` —— 别搞混

这个知识点最容易和什么搞混？一句话点破。

> 重力 与 质量：重力会随地点变（月球上是地球的 1/6），质量到哪都不变——质量是「有多少东西」，重力是「被拉多紧」。

### 5.5 `everyday` —— 生活里在哪见

具体的、中国人日常能碰到的场景，**不要和 analogy 举同一个例子**。

> 公交车急刹车人会往前扑——不是有只手推你，是你还在往前，车已经停了。

### 5.6 `selfCheck` —— 自检三问

从易到难：

1. 考「是不是」
2. 考「为什么」
3. 考「换个条件还成立吗」

答案要说清思路，不只是给结论。

### 5.7 三条硬规矩

| ❌ 不要 | 为什么 |
|---|---|
| 改 `id`、`knowledgeId`、`misconceptionId` | 这些是胶水，改了别处全断 |
| 改 `.ts` / `.tsx` 文件（除非是 `question-bank.ts` 的 `HANDWRITTEN` 数组） | 那是代码，改了网站会崩 |
| 用 AI 生成整段直接粘进去 | 你要先自己看懂。这是给学生看的 |

## 6. 用 AI 助手帮你干活，怎么用才对

你有 agent 帮忙是好事，但**要用对地方**。

### ✅ 适合让 AI 做的

- **查格式**：「帮我检查这个 JSON 有没有语法错误、有没有尾逗号」
- **数字数**：「这段 detail 有多少字？有没有超过 200 字？」
- **查重复**：「这条 everyday 和 analogy 是不是举了同一个例子？」
- **跑自检**：「跑一下 `node shared/knowledge-data/schema/validate.mjs`，把报错翻成人话告诉我」
- **查覆盖率**：「哪些知识点还没有挂误区？」
- **润色**：「这段话我写得有点绕，帮我改通顺，但不要改意思」
- **批量查找**：「在 card-detail 六个文件里，有哪些条目的 selfCheck 不是 3 条？」

### ⚠️ 要小心的

- **让 AI 从零写物理内容**。它会写得很像样，但物理经常是错的——尤其是热学（熵、效率）和近代（量子、能级）。**它写完你必须逐条对着课本核。**
- **让 AI 一次改很多条**。改 3 条你还能核得过来，改 30 条你核不动，错了也发现不了。
- **让 AI 决定「这条要不要写」**。哪些知识点重要、哪些误区真实，只有人知道。

### ❌ 不要让 AI 做的

- **改代码**（`.ts` / `.tsx` / `.mjs`）。这个项目有 41 条物理断言测试，AI 改代码很容易把测试改崩。
- **决定物理模型的标注**（可计算 / 近似 / 仅示意）。这是平台对学生的承诺，必须人来定。
- **提交 git**。你改完发给 A，A 负责提交和部署。

### 一个靠谱的用法示例

```
你：读一下 shared/knowledge-data/card-detail/thermodynamics.json，
    告诉我哪些条目的 detail 第三段提到了「平台做不出这个实验」。

AI：（列出条目）

你：好，把这 12 条的第三段贴出来给我看，我要逐条核。

AI：（贴出来）

你：（逐条读，发现第 5 条说错了）

你：帮我把 K-T2-03 那一条的第三段改成这样：「……」（你自己写好）

AI：（改好，跑 JSON 校验，报告通过）

你：（再读一遍改后的内容，确认没问题）
```

**关键：AI 打字，你判断。永远不要反过来。**

## 7. 怎么检查你改的东西

在项目根目录跑：

```bash
node shared/knowledge-data/schema/validate.mjs
```

它会检查四件事：

| 输出 | 意思 | 怎么办 |
|---|---|---|
| `✗ 缺字段 why` | 必填字段空了 | 补上 |
| `✗ 引用了不存在的误区 MIS-O2-4` | 编号打错了（少一个 0） | 改成 `MIS-O2-04` |
| `✗ 前置 K-O2-99 不存在` | 指向了没编号的知识点 | 改对，或者问 A |
| `⚠ why 字段太短` | 提醒，不是错误 | 建议写长点 |

`✓ 全部通过` 就说明没写坏。

**写坏了不会把网站弄坏**——这个脚本只报告，不改你的文件。

还有一个检查卡片是否齐全的：

```bash
node scripts/gen-knowledge-cards.mjs
```

它会重新生成 `knowledge-cards.json`，并且告诉你生成了多少张。如果条数变少了，说明某个 id 写错了。

## 11. 一句话总结

**你要做的不是「把内容写多」，是「把学生看不懂的地方写清楚」。**

判断标准很简单：**把这段读给一个没学过物理的成年人听，他能听懂吗？** 听不懂就重写。
